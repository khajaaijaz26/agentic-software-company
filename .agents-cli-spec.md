## Overview

Software Agent is a local-first terminal application that turns one developer
prompt into a governed software-delivery run performed by visible specialist
agents. A user installs one npm package, opens a repository, runs
`software-agent`, chooses a provider/model, and works inside a persistent,
keyboard-driven project room.

The terminal truthfully shows which agent owns each task, its current committed
state, selected model, token/cost usage, requested files/tools, handoffs,
evidence, blockers, and approvals. Status comes from controller projections;
transient animation or uncommitted model text cannot imply progress.

Users bring their own API credentials. ChatGPT and Claude consumer subscriptions
are not API credentials; provider API usage is separately billed by the
provider. Software Agent does not resell model access.

## Post-publication journey

After the registry release gate, the intended primary journey is:

```text
npm install --global software-agent
cd an-existing-project
software-agent
```

Before publication, documentation must label the following as development-only:

```text
npm ci
npm run check
npm pack --json
npm install --global ./software-agent-0.3.0.tgz
```

The interactive journey is:

1. First-run provider connection and model selection.
2. A prompt composer for the requested change.
3. A proposed task graph from the Master Orchestrator.
4. Deterministic controller validation and explicit plan approval.
5. Concurrent specialist work with live side-by-side agent cards.
6. Agent-specific tool/risk approvals with exact operation previews.
7. Independent review, tests, evidence, and final handoff in the same terminal.
8. Durable runs that can be left and joined again without losing history.

## Terminology and identifiers

- **Workspace** (`wsp_...`): one canonical local project root and its
  `.software-agent/` state.
- **Run** (`run_...`): one user objective, validated task graph, budget, and
  terminal outcome.
- **Agent Session** (`ags_...`): durable role-scoped conversation/context inside
  one run.
- **Agent Turn** (`trn_...`): one immutable input-to-intent cycle in an Agent
  Session.
- **Task Assignment** (`asn_...`): controller-owned binding of one task revision
  to one Agent Session.
- **Worker Attempt** (`att_...`): disposable process execution of one Agent Turn.
- **Model Invocation** (`mdl_...`): one broker-owned provider request.
- **Tool Call** (`tol_...`): one typed requested operation and its journal.
- **Mailbox Message** (`msg_...`): durable question, answer, instruction, or
  handoff payload.
- **UI Attachment** (`uia_...`): one terminal connected to a run/project room.
- **Mutation Lease** (`mut_...`): fenced right for one UI Attachment to issue
  mutating operator commands.

`software-agent run join <run-id>` joins a project room. The command does not
call a Run, Agent Session, or UI Attachment a generic "session."

## Authority and component architecture

The TypeScript controller and its SQLite database are the sole authority.
The Master Orchestrator proposes a DAG, assignments, and handoffs; the
deterministic controller validates them, and the scheduler owns authoritative
state transitions.

```text
Interactive CLI/TUI or headless CLI
              |
              | commands + cursor-based committed events
              v
Authenticated local IPC gateway
              |
              v
Controller command bus (short validation/commit sections only)
  |             |              |                 |
  v             v              v                 v
scheduler   agent coordinator  approval/tool     model broker
  |                            executor              |
  v                                |                 v
fenced step workers          environment ports   provider APIs
              \                 /                  /
               \---- typed results/intents -------/
                              |
                              v
                  controller transaction coordinator
                              |
                              v
        SQLite run aggregate, projections, budgets, artifacts
```

Only quick validation and event/ledger commits are serialized. Provider, worker,
and tool I/O happens outside the writer lock under committed, expiring, fenced
grants. Completion is revalidated before a short commit. This preserves single
authority without serializing concurrent work.

### Phase A atomicity model

One Run stream is the aggregate root for task, assignment, agent-session, turn,
attempt, model, mailbox, handoff, question, tool, approval, and run transitions.
A controller transaction coordinator uses one SQLite connection and one
`BEGIN IMMEDIATE` unit for each mutating command. Event append, command receipt,
projection update, approval consumption, budget reservation, tool journal
transition, operation hash, and idempotency key commit together when they are
part of the same authority decision.

Every mutating command carries a caller-generated `commandId`, actor,
`expectedRunRevision`, correlation ID, causation ID, UI Attachment ID, and
Mutation Lease fencing token. Reusing a command ID with different canonical
input fails closed.

## First shippable agents and graph

Phase A activates three stable roles:

- `master-orchestrator`: proposes the task graph, assignments, handoffs, and
  final summary. It has no direct file/shell authority.
- `software-engineer`: maps to the existing `backend-engineer` prompt during
  migration, then receives a dedicated prompt/capability contract for bounded
  repository inspection and patch proposals.
- `reviewer-qa`: composes the existing `code-reviewer` and `qa-strategist`
  responsibilities under a dedicated read/test/review contract.

The first graph proves real concurrency:

```text
intake-and-plan
     | approval
     +---------------------------+
     v                           v
implementation              test-plan-and-risk-review
     |                           |
     +-------------+-------------+
                   v
             final-independent-review
                   |
                   v
             evidence-and-handoff
```

The engineer and reviewer may run overlapping read/model turns. Only one
workspace mutation lease exists, so parallel reasoning does not permit
conflicting writes. A handoff offer keeps ownership with the sender until the
receiver atomically accepts; reject, timeout, and duplicate acceptance are
explicit terminal outcomes.

The existing 25-role catalog stays discoverable. Phase B must implement and
test execution contracts for the remaining 22 roles before any are advertised
as runnable.

## Durable step protocol

`software-agent.step/v1` is versioned independently of IPC and database schema.

1. Controller commits a `StepManifest` containing run/task/session/turn IDs,
   task revision, attempt/lease IDs, fencing epoch, workspace revision,
   provider/model routing revision, allowed intent types, context artifact
   digests, token/cost grant, deadline, and output limits.
2. Worker starts with a scrubbed environment, sends `worker.hello`, validates
   the manifest, and returns `worker.accepted`.
3. Worker requests a model turn through an attempt-bound local broker
   capability. Credentials never cross to the worker.
4. Controller broker atomically reserves budget, calls the provider outside the
   writer lock, validates normalized frames, commits bounded progress/usage,
   and returns normalized output to the worker.
5. Worker may emit typed intents: tool request, question, handoff offer,
   evidence, completion, or failure. Provider deltas are broker output, not
   worker authority.
6. Worker sends durable heartbeat/checkpoint frames at a bounded interval.
7. Controller accepts a final result only when run/task/session/turn revision,
   attempt, lease, and fencing epoch still match.
8. Cancellation is acknowledged; a late result is retained as diagnostic
   evidence but cannot transition authoritative state.

Workers never persist state, resolve secrets, call providers directly, or
execute host tools directly.

## Durable contracts and projections

Phase A defines versioned commands, events, statuses, revisions, and schemas for:

- Run and task graph;
- Agent Session and Agent Turn;
- Task Assignment;
- Worker Attempt, lease, heartbeat, checkpoint, and fencing epoch;
- Model Invocation and normalized usage;
- Tool Call, authorization, execution journal, and postcondition;
- Mailbox Message;
- Handoff offer, accept, reject, and expire;
- Pending Question and single-use Answer;
- UI Attachment and Mutation Lease;
- Context Manifest, checkpoint, and summary; and
- Token/cost budget reservation, reconciliation, and extension.

Projections show task/agent state separately from worker liveness. A running
assignment with an expired heartbeat renders `STALE / RECOVERING`, including
attempt ID, lease expiry, last heartbeat, blocked reason, and last applied event
sequence; it never appears actively working.

Instructions submitted during an active turn queue for the next turn. An answer
must bind a specific question ID and is consumed exactly once.

## IPC event delivery

IPC protocol `software-agent.ipc/v2` keeps the authenticated local socket/pipe
boundary and adds cursor delivery.

- `snapshot.get` returns a bounded projection plus the authoritative global
  sequence cursor, never complete event history.
- `events.subscribe` atomically registers after that cursor so snapshot plus
  subscription has no race.
- Each subscription has an ID, filters, monotonic sequence validation,
  deduplication, explicit unsubscribe, and serialized outbound writes.
- Per-client queue is bounded to 512 events or 512 KiB, whichever is first.
- A slow client or missing cursor receives `RESYNC_REQUIRED`; it must request a
  new snapshot rather than guessing.
- History is paginated at at most 250 events and bounded by the existing 1 MiB
  frame limit.
- Committed domain events drive state. Optional transient text deltas are
  separately labeled, bounded, droppable, and cannot change status.
- Unauthorized peers, replayed proofs, stolen descriptors, malformed frames,
  and incorrect workspace/user bindings are rejected before RPC dispatch.

Phase A includes owner-only Unix socket permissions and Windows named-pipe ACL
plus peer identity verification. Authentication nonce/descriptor files remain
owner-private and replay resistant.

## Controller lifecycle and recovery

`software-agent` starts a detached, hidden, package-installed controller when
none owns the workspace, waits for recovery readiness, then attaches the TUI.
The controller remains alive while a run is active. With no active run and no UI
Attachment, it exits after 30 minutes. Explicit commands are
`software-agent daemon status|start|stop`.

`run resume` commits an accepted command and returns immediately; scheduling is
background work, never a run-length RPC. Startup recovery completes before the
controller accepts mutations. Graceful shutdown stops dispatch, requests
attempt checkpoints/cancellation, waits within a bounded grace period, marks
uncertain work for reconciliation, flushes committed state, and then closes
SQLite.

### Recovery decision matrix

| Crash boundary | Required recovery |
| --- | --- |
| Lease committed before worker start | expire/fence attempt, create a new attempt without duplicating a turn |
| Provider accepted request or partial stream before receipt commit | mark invocation `OUTCOME_UNKNOWN`; never auto-retry; user/controller reconciliation decides and billing may be uncertain |
| Tool authorized before execution start | safe to resume only if authorization remains valid and no execution journal start exists |
| Tool execution started before result commit | verify adapter postcondition; retry only with proven idempotency, otherwise `NEEDS_RECONCILIATION` |
| Worker result received before event commit | idempotently re-submit the bound result using the same command ID |
| Pause/cancel requested before acknowledgement | stop new dispatch, terminate bounded process tree, then commit final pause/cancel or `NEEDS_RECONCILIATION` |

The guarantee is no duplicate **committed Agent Turn**. A remote provider may
charge for an outcome-unknown request; the product must show that uncertainty
rather than claim impossible exactly-once network execution.

## Repository concurrency and safety

- Model/read turns may overlap, but Phase A permits one controller-owned
  workspace mutation lease at a time.
- Patch proposals bind repository revision and expected SHA-256 for every
  changed file. Application is atomic per patch set.
- Dirty and untracked files are inventoried at run creation and never deleted or
  overwritten. They remain user-owned.
- External edits, revision drift, or hash mismatch pause the affected task and
  require re-read/replan. No force application is allowed.
- Patch conflicts produce a reviewable artifact; they do not trigger automated
  conflict resolution against unknown user changes.
- Test commands come only from validated project configuration or an exact
  approval. Tests bind a stable workspace revision.
- Before final acceptance, the user can view the exact diff, files, tests,
  evidence, and rollback boundary.
- Phase A implements bounded Windows Job Object / POSIX process-group
  containment for workers and test commands. Stronger OS sandboxing remains
  Phase C.

## Provider, model, and BYOK design

Phase A ships only:

- OpenAI native Responses API adapter; and
- Anthropic native Messages API adapter with an explicitly pinned
  `anthropic-version` header.

SDK versions and wire fixtures are locked in `package-lock.json`; upgrades
require adapter contract tests and release notes. Provider model-list APIs are
treated as basic identity discovery only. A versioned adapter-maintained
capability/pricing catalog records source and timestamp. Unknown capabilities,
limits, or prices stay `UNKNOWN`; they are never inferred from a model name.

The controller owns a local model broker:

```text
worker request -> attempt-bound broker grant -> policy/data-boundary check
               -> atomic budget reservation -> secret lease -> provider API
               -> normalized frames/usage -> bounded worker result
```

Raw credentials necessarily exist transiently in broker memory and outbound
authorization headers. They are never persisted, logged, placed in IPC,
included in prompts, or propagated to worker/tool child processes.

### Credential configuration

- Windows: Credential Manager backend.
- macOS: Keychain backend.
- Linux desktop: Secret Service backend.
- Headless/CI: user-global `env://VARIABLE` reference.
- If the credential store is unavailable, fail with guided `env://` setup;
  never fall back to plaintext.
- Interactive add uses a non-echoing hidden prompt. Automation may use explicit
  `--api-key-stdin`; secret values are never accepted as argv.
- Create, test, rotate, remove, permission-denied, and unavailable-store paths
  have platform tests.

Repositories may select provider/model IDs but cannot supply credential
locators, endpoints, or secret-manager references. Those live only in
user-global configuration. A repository-requested provider or data-boundary
change requires explicit human consent.

For `env://`, the controller resolves the variable from its own startup
environment and deletes that key from `process.env` before accepting work.
Worker/tool environments are built from an allowlist and never inherit provider
key variables.

### Model selection and routing

Selection precedence is:

1. Per-run `--model`.
2. UI selection for the next run.
3. Per-role route.
4. Project default provider/model ID.
5. User-global default.

Run start pins routing revision 1, requested model, catalog snapshot, and
fallback policy. An explicit model change during a run creates a new audited
routing revision and applies only to future, unleased Agent Turns. Every
response records the provider's actual resolved model because aliases may drift.

Cross-provider fallback is disabled by default. No fallback occurs after any
partial stream. A configured fallback requires a policy/data-boundary check and
new budget reservation; potential duplicate charges are surfaced.

Required commands/TUI actions:

```text
software-agent providers add openai
software-agent providers add anthropic
software-agent providers list
software-agent providers test <provider>
software-agent providers rotate <provider>
software-agent providers remove <provider>
software-agent models list [--provider <provider>]
software-agent models use <provider>/<model> [--scope user|project|next-run]
software-agent models current
software-agent run --model <provider>/<model> "request"
/connect
/models
```

## Token efficiency and race-safe budgets

### Normalized accounting

Default full run ceiling is 100,000 billed tokens and is configurable from
1,000 to 10,000,000. Modes select an effective ceiling:

- `economy`: 25,000 tokens (25% of default full ceiling);
- `balanced`: 50,000 tokens (50%, default); and
- `quality`: 100,000 tokens (100%).

For a custom full ceiling the same percentages apply. Initial per-agent shares
are 25% orchestrator, 50% engineer, and 25% reviewer; unused share may be
atomically reassigned without exceeding the run ceiling.

Provider `total_tokens` is authoritative when valid. Otherwise normalized
billed tokens are input plus output. Cached input is a subset of input and
reasoning is a subset of output unless the provider explicitly reports a
separate billed total; displayed subcategories are never added twice.

Before each provider call, the controller atomically reserves estimated input
plus requested maximum output across all concurrent agents. It reconciles to
valid reported actual usage. Partial, canceled, malformed, or unknown usage
retains the full reservation as `UNKNOWN` until reconciled. Retries require a
new reservation and never hide prior possible billing.

At 80% of the effective ceiling the TUI warns. At 100%, new paid calls pause.
In default balanced mode this is 50% of the configured full ceiling. An exact,
single-use approval may add one 25%-of-full increment, expires in 15 minutes,
and can extend at most to the configured full ceiling. Denial preserves an
evidence-backed partial result.

Context occupancy is separate from cumulative spending. Before a turn, the
broker requires estimated input + maximum output + tool-result reserve to fit
within 80% of the model context limit. If not, a budgeted checkpoint/summary and
retrieval step reduces input; already spent tokens are never described as
recovered. A stable prompt prefix, task-scoped context manifests, incremental
file retrieval, content-addressed deduplication, bounded tool results, and
persisted summaries reduce repeated input. Waiting for approval produces zero
repeated paid model turns.

### Token-efficiency benchmark

`evals/token-efficiency/v1/` pins repository commits, at least 10 tasks,
provider/model identifiers and resolved versions, parameters, routing, retry
policy, baseline prompts, raw usage, and quality rubrics. Each candidate and
naive full-context baseline runs three times. Release requires:

- median candidate input tokens <= 50% of baseline median;
- no task candidate median > 75% of its baseline;
- >= 90% rubric pass rate for both candidate and baseline; and
- no candidate correctness regression greater than one rubric point.

No universal "50% cheaper" marketing claim is allowed without this published
evidence.

## Tool and approval flow

Phase A host tools are bounded repository listing/search/read, atomic patch
application, Git status/diff inspection, and approved configured test commands.
Network egress is limited to the selected model provider. GitHub, Vercel,
Supabase, arbitrary shell/network, and production mutations are not Phase A
execution capabilities.

Every tool request follows:

1. Agent emits a typed intent with purpose, target, and expected output.
2. Controller validates schema, assignment, task revision, repository hashes,
   paths, and capability.
3. Global guard middleware applies to every agent and tool boundary.
4. Policy classifies the exact operation A0-A5.
5. Budget/approval services reserve or suspend transactionally.
6. Tool Gateway executes through a fixed Environment Port with timeout, output
   limit, process containment, terminal sanitization, and idempotency key.
7. Output is stored as an artifact/receipt; only a bounded projection enters
   later model context.
8. Controller commits the result and resumes the exact suspended Agent Turn.

Approval classes remain:

- A0 observe/read-only: may proceed within policy.
- A1 reversible local mutation: may proceed within workspace policy.
- A2 reversible isolated remote mutation: exact approval required.
- A3 shared non-production mutation: exact approval required.
- A4 production/security-sensitive mutation: exact approval plus critical
  confirmation required.
- A5 destructive/irreversible: denied by default; named hard denials remain.

An approval packet includes requester agent/actor, purpose, exact operation,
paths/target, scope, risk/class, impact, data boundary, token/cost budget,
operation hash, idempotency key, preconditions, expected postcondition,
rollback/reconciliation plan, evidence, expiry, and changed-since-request
status. Decisions are approve, deny with reason, or request changes. A4/A5
confirmation requires typing the displayed operation label; no one-key approval.

## Interactive terminal contract

Running `software-agent` in a TTY opens a persistent Ink project room.

### Layout breakpoints

- width < 60 or height < 20: stable plain fallback, no cursor UI;
- width 60-89: narrow single-card/detail view;
- width 90-119: compact two-card view; and
- width >= 120: standard three-card view.

All layouts have text labels independent of color, honor `NO_COLOR` and
`--no-color`, support ASCII fallback, sanitize terminal control text, preserve
focus/selection across resize/reconnect, and restore terminal state after clean
exit, error, or handled signal.

### Project room

- Header: workspace, branch, run, controller/connection health, provider/model,
  configured/effective token ceiling, consumed/reserved tokens, and cost.
- Agent area: responsive cards with role, state, task, activity, elapsed/waiting
  time, provider/model, tokens/cost, attempt/heartbeat, blocker/approval/question,
  tools/files, and evidence.
- Event area: committed important events with search/filter/follow.
- Detail area: selected agent/task/diff/artifact/tool/approval.
- Composer: visible target (`new run`, agent, task, or question) and input.
- Footer: only implemented shortcuts.

If no target is selected during an active run, composer submission opens a
target picker; it never broadcasts implicitly. Loading, empty, reconnecting,
read-only, cursor-gap/resync, controller-recovery, controller-failure, and stale
worker states have explicit screens. A recent-runs picker removes the need to
remember IDs.

### Keymap

- `Tab` / `Shift+Tab`: next/previous pane.
- Arrow keys or `h/j/k/l`: selection and scrolling outside composer.
- `1` dashboard, `2` agents, `3` tasks, `4` approvals, `5` events.
- `c`: focus composer; `Ctrl+K`: command palette; `/`: search when composer is
  not focused; `f`: toggle event follow; `?`: help.
- `Enter`: open/select; `Esc`: close/back; `a`: open selected approval detail;
  `d`: open selected diff.
- `Ctrl+C`: first opens leave/pause/cancel choice while work is active; second
  forced interrupt follows recovery rules.

Normal text creates an objective when no Run exists. During a Run it becomes a
versioned targeted instruction or consumes a selected Question. `/...` invokes
commands with completion and side-effect preview; `//text` sends a literal
leading slash.

Approval UX is inbox -> complete packet -> decision -> confirmation. Focus modes
are navigation, composer, palette, search, and confirmation so typing cannot
trigger global shortcuts.

### UI mutation lease

One UI Attachment holds a Mutation Lease with 15-second TTL, renewal every 5
seconds, and a monotonic fence. Disconnect expiry allows another attachment to
acquire it after a 10-second grace. Read-only attachments may view, search,
follow events, and export non-sensitive evidence; they cannot instruct,
approve, change models/budgets, pause, cancel, or mutate files.

## Data, memory, and prompt efficiency

Agent Sessions keep isolated context. Stable policy/role/tool instructions form
a byte-stable cacheable prefix; project/task context is a bounded manifest; turn
state is a volatile tail. Durable summaries persist only task decisions,
explicit user instructions, repository facts with source revision, handoffs,
and evidence references. Raw secrets and unrestricted conversation replay are
never memory.

Global safety middleware runs before user input persistence, before/after every
tool, and after model output. Unsafe or secret-bearing content is replaced by a
typed blocked record before it can poison later session context.

## Security constraints

- Only the controller commits durable state or performs host/provider effects.
- Models/workers propose typed intents; they cannot approve authority.
- Secrets are transient only in the controller broker and provider header.
- Unknown operations/capability drift fail closed.
- Approval/tool/budget actions commit atomically where authority changes.
- Provider calls enforce fixed HTTPS origins, DNS/TLS validation, no redirects,
  abortable deadlines, response limits, safe retry rules, and redacted errors.
- Model, repository, attachment, and tool content is untrusted and terminal
  sanitized.
- Cross-provider fallback/data-boundary changes require explicit consent.
- A0-A5 hard denials from v0.2 remain.
- Arbitrary npm plugins are not loaded in v0.3.
- The Python/MCP compatibility runtime never becomes a second controller.

## Distribution and release

The registry name `software-agent` was not publicly found during planning, but
availability is not ownership. Publication is blocked until the owner logs into
npm, enables 2FA, and successfully claims it. No documentation may claim it is
published before registry verification.

Bootstrap release:

1. Run all A1-A8 gates from a clean tagged commit.
2. Owner performs the initial public publish with npm authentication/2FA.
3. Verify registry name, public access, executable, tarball contents, checksum,
   provenance visibility, and clean global install.
4. Configure npm trusted publishing for the exact GitHub repository/workflow.
5. Subsequent protected tag releases use GitHub-hosted Node 24, npm >=11.5.1,
   `id-token: write`, public access, and automatic provenance.

CI derives the tarball filename from `npm pack --json`, scans it for secrets,
checks executable mode, installs it globally on Windows/macOS/Linux, launches
the packaged detached daemon, and verifies restart. Release tests enforce tag,
package version, lockfile, repository URL, changelog, and schema compatibility.

## Assumptions selected by the owner or delegated to the implementer

- API-native providers are the primary engine; third-party coding CLIs are
  optional Phase C bridges.
- OpenAI and Anthropic are the only Phase A live providers.
- Balanced mode pauses at 50% of the configured full token ceiling and asks for
  exact human extension approval.
- The product is local-first and single-user per workspace.
- Public package name and executable target `software-agent`; registry ownership
  and first publish require the owner's npm login/2FA.
- GitHub repository rename to `software-agent` occurs only after Phase A passes.
- Original raster visuals are required, while screenshots must come from the
  implemented UI and accurate diagrams remain code-native.
- Clarity, polish, distribution, examples, and community tooling support
  developer reach; popularity is not guaranteed.
